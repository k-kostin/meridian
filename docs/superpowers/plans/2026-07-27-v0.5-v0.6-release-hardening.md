# v0.5 / v0.6 Release Hardening Long Session Plan

> **For agentic workers:** Execute this plan task-by-task. Keep the existing domain core, do not add Stage E product features, and stop after 3-4 meaningful failed attempts on the same blocker to reframe instead of looping.

**Goal:** Resolve the July 2026 audit findings, close the code-solvable part of `v0.5.0`, and leave `v0.6.0` ready for a mechanical real-Windows validation session.

**Architecture:** Preserve one Django domain core for both commercial profiles. Keep SQLite and trusted localhost access for `Local Single User`; keep authenticated server deployment as a separate future profile. Electron remains orchestration only. All stock invariants, imports, audit events, attribution, backups, and exports remain in Django services/models.

**Tech Stack:** Django 6, SQLite, openpyxl, Waitress, PyInstaller onedir, Electron, electron-builder NSIS, Node.js contract scripts, GitHub Actions, browser smoke tests.

---

## 1. Session Objective

The session is complete only when:

1. A backdated issue or transfer cannot make any later daily balance negative.
2. A clean Electron installation has an explicit, tested `Local Single User` access profile and can perform the first real operation without creating a Django user manually.
3. Excel import commit, attribution, and activity recording have truthful transactional semantics.
4. Automatic backups happen only when needed and have bounded retention.
5. Electron dependencies and Windows build inputs are reproducible.
6. User-controlled Excel text cannot be emitted as executable spreadsheet formulas.
7. Core documentation, versions, release gates, and GitHub verification match the code.
8. The verifier stack and a fresh-data-dir browser smoke pass.

The session does **not** claim:

- completion of validation against real client `.xlsx` files;
- completion of a real Windows NSIS installation;
- completion of `v0.6.0`;
- production-grade RBAC, PostgreSQL multi-user mode, or Stage E analytics.

## 3. Working Rules

1. Use separate reviewable PRs for independent risk areas.
2. Write failing regression tests before changing each business invariant.
3. Do not mix Stage E features or UI redesign into these PRs.
4. Preserve demo mode behavior.
5. Preserve authenticated server behavior: anonymous production web users remain viewers unless the explicit local desktop profile is enabled.
6. Do not silently swallow audit failures.
7. Never delete manual backups automatically.
8. Do not mark manual Windows or real-client Excel gates as passed from macOS.
9. After each PR:
   - run targeted tests;
   - run the full verifier;
   - create the PR;
   - inspect Gemini review comments;
   - address actionable comments before merge.
10. Keep `main` green between slices.

Recommended branches:

- `v0.5-stock-invariants`
- `v0.5-import-consistency`
- `v0.5-desktop-hardening`
- `v0.5-release-gate`

## 10. Failure Budget and Stop Conditions

Stop and re-plan instead of improvising when:

- the same defect survives 3-4 materially different fixes;
- temporal balance validation requires changing the meaning of operation dates;
- local trusted mode cannot be constrained to loopback packaging safely;
- migrations or backup tests require destructive access to a real user database;
- Electron packaging needs a major-version upgrade unrelated to the audit;
- a Gemini comment reveals a domain-level ambiguity rather than an implementation defect.

Never resolve those situations by:

- weakening tests;
- enabling demo mode in production;
- allowing negative stock silently;
- swallowing audit exceptions;
- deleting backups broadly;
- claiming a manual Windows/Excel gate passed.
